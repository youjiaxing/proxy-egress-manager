# 首次发布准备

首版 `v0.1.0` 已按用户授权发布，对应 `pyproject.toml` 的 `0.1.0` 与源码提交 `a3b35e97ab8decc45bcf916724154cfd94dfe8c4`。固定镜像引用见 [部署](deployment.md)，实际发布验证见 [验证记录](verification.md)。以下流程用于后续显式发布。

## 显式发布流程

1. 确认 GitHub 账号或组织及仓库名，将已检查的源码提交推送至公开仓库。不要上传 `.env`、订阅、数据卷或备份。
2. 等待 CI 的原生 Linux amd64 / arm64 测试、镜像构建及实际 Compose 启动全部通过，核对其提交就是拟发布提交。
3. 在同一提交创建稳定版本 `v0.1.0` 的 GitHub Release。仅此操作触发 GHCR 发布；普通 push 不发布，发布也不会升级服务器。发布流程再次复用同一提交的完整双架构 CI，包含真实核心、镜像构建和 Compose 启动。既有版本标签禁止覆盖：只有两个架构的源码 revision 均匹配当前提交时，重跑才读取原摘要并补交发布附件，跳过构建和推送；不匹配或注册表权限、网络检查不明确时拒绝继续。
4. 等待发布工作流的两架构测试与镜像构建成功，保存 Release 附件 `deployment-reference.txt` 中的 `ghcr.io/<账号或组织>/proxy-egress-manager:v0.1.0@sha256:...` 与源码提交。核对构建来源、SBOM、许可证与发布提交。若镜像推送已成功而附件上传失败，重跑会验证既有镜像两个架构的源码 revision、读取原摘要并补传附件，不重新构建或覆盖标签。已有附件只核对内容一致，不覆盖。
5. 核验 GHCR 包可见性为公开，并用没有登录凭据的客户端实际拉取固定摘要；首次包可能需要所有者单独调整可见性。分别核查两个架构条目。失败时不要将其视为可部署版本。
6. 交付版本对应的 Compose、空白环境示例、不可变镜像引用和部署文档。真实服务器启动仍按单独授权执行，参见 [部署](deployment.md)。

## 升级和回滚

按 [维护流程](operations.md) 操作：预拉新镜像，记录旧摘要及部署配置，停止整个项目，使用旧镜像做离线一致备份，再切换版本并重建。回滚时停止新版本，恢复旧版本配置与升级前备份，重新初始化并验证。不要删除数据卷；回滚会丢失备份点之后的配置及历史。

首版没有已发布的旧镜像可回滚。首次启动失败时停止项目、保留诊断和数据；若尚无真实配置，可在确认范围后重新初始化测试数据。不得假定存在可用历史版本。
